## 3. Defect A — PJ amount routed to CDJ Professional Fee

### Reported
A PJ amount lands in the CDJ **Professional Fee** column even when the transaction belongs under
**Sundry Account** and its actual account title.

### Root cause (confirmed)
`modEngine.bas` `SyncPJToCDJ` sundry branch — both the *update* and *insert* paths:

```
' modEngine.bas:519-521  (and identically :555-557)
' Sundry (col 19 = S): COA label text in col S, amount in col R (18)
.Cells(targetRow, CDJ_EXPENSE_END).Value      = description   ' S = sundry title  (correct)
.Cells(targetRow, CDJ_EXPENSE_END - 1).Value  = netAmount     ' R = 18 = PROFESSIONAL FEES  (WRONG)
.Cells(targetRow, CDJ_COL_DEBIT).Value        = grossAmount   ' T = sundry debit = gross    (WRONG)
```

`CDJ_EXPENSE_END - 1` = column 18, which the workbook header labels **"Professional Fees"**
(`CDJ!R13="Professional "`, `CDJ!R14="Fees"`).

### GL impact (why the balance gate cannot catch it)
`modGLScanEngine.ScanCDJ` (`modGLScanEngine.bas:107-121`) iterates fixed allocation columns
`c = 7 To 18` and maps column 18 through `V8_CDJMap(18) = "Professional Fees"`
(`modGLWorkbookMap.bas:77`). The sundry block then derives

```
sundryNet = (-cash) + otherCr - otherDb          ' :135
```

With `cash = -gross`, `otherDb = VAT + net = gross`, `sundryNet = 0`. So:

- the **entire net amount posts to Professional Fees**;
- the Sundry Account title receives **0.00**;
- debits still equal credits, so the fail-closed reconciliation gate (`:34`) passes.

This is a **silent misclassification**, not a visible failure.

### Reproduction — real rows in the candidate workbook

| CDJ row | E (Particulars) | R = col 18 | S = sundry title | T = debit | X = balance check |
|---|---|---|---|---|---|
| 632 | YVES ROCHER | **534.8214285714286** | Miscellaneous | 599 | **+599.00 (≠ 0)** |
| 633 | YVES ROCHER | **1600.8928571428569** | Miscellaneous | 1793 | **+1793.00 (≠ 0)** |
| 634 | BACCHUS CATERING CORP | **891.0714285714284** | Representation | 998 | **+998.00 (≠ 0)** |
| 636 | NONOS | *(empty)* | Miscellaneous | 2253.5714285714284 | 0 (correct shape) |
| 670 | YVES ROCHER | *(empty)* | Miscellaneous | 534.8214285714286 | 0 (correct shape) |
| 672 | BACCHUS CATERING CORP | *(empty)* | Representation | 891.0714285714284 | 0 (correct shape) |

Correct shape: `S = title`, `T = net`, `R` empty, `X = 0`.
Buggy shape: `R = net`, `T = gross`, `X = net ≠ 0`.

### Secondary defect in the same routine
The fixed-column branch (`modEngine.bas:514-515` and `:550-551`) writes **net into the allocation
column *and* gross into T**. Row 630 (WATSONS) shows the result: `N630 = 2678.57` **and**
`T630 = 3000` → `W630 = SUM(G:T) = 6000` vs `V630 = -3000` → **`X630 = +3000 ≠ 0`**.

### Additional consequence
`CDJ_COL_NOTE = 24` (`modEngine.bas:49`) writes the entry-log text over column X, which is the live
row-balance formula `=V+W`. Every sync therefore destroys its own balance check.

### Acceptance tests for the fix
- A PJ transaction classified to a non-professional-fee account is **not** written to column R.
- The amount is preserved numerically and lands in column T (Sundry Debit).
- Its destination account title matches the sundry label in column S.
- Existing Professional Fee transactions (e.g. CDJ row 638, `SBM Consulting`) continue to work.
- `X` (row balance check) evaluates to 0 for every machine-written row.
- Unresolved classifications remain visible and auditable rather than defaulting to Professional Fee.

## 4. Defect B — supplier TIN misread / wrong value in vendor-name field

### Reported
Some supplier TINs are not recognized, or appear in the vendor-name field.

### Confirmed causes

**B1 — exact-string TIN dictionary keys (no normalization).**
`modEngine.bas:152,156` build `dictTIN` from raw `Trim(ws.Cells(i,3).Value)`; lookup at
`:315-317` is an exact, case-sensitive `Exists`. The same pattern exists in `Sheet12.cls:65-66`,
`Sheet11.cls:65-66` and `modPJSync.bas:159`.

Reproduction: the master contains the malformed key `009-149--884` (double dash) at
`SUPPLIERS DATA!C34`, and it is copied into live data at `PJ!D42`. A correctly-typed
`009-149-884` **does not resolve**. Dash-less (`008888659`) and branch-suffixed
(`226-784-068-000` vs `226-784-068`) variants are likewise distinct keys.

**B2 — last-row-wins on duplicate TINs clobbers the vendor name.**
`LoadSuppliers` (`modEngine.bas:156`) overwrites on collision. `SUPPLIERS DATA` holds **34 TINs
shared by 2–4 different companies**, e.g.:

| TIN | Companies sharing it |
|---|---|
| `252-126-611` | EUROFUEL INC (row 9), FACIAL CARE CENTRE (row 112) |
| `008-909-992` | SOUTHEASTASIA RETAIL INC, LANDERS, SPEAR ONE RESTAURANT INC |
| `000-388-771` | JOLLIBEE 39TH, JOLLIBEE BLUEBAY WALK, JOLLIBEE, M9S PETROLEUM CORP |
| `207-961-175` | SAVEMORE, FESTIVAL MALL, SHAKEYS PIZZA |

`Sheet12.cls:68` then writes the resolved name back into **`PJ!E` (Vendors' Name)**. This is the
mechanism by which an "unrecognized" TIN produces a wrong value in the vendor-name field — the TIN
itself never migrates into E; the *name* is the field that is corrupted.

**B3 — literal `TIN NOT FOUND` placeholder in the master.**
`SUPPLIERS DATA!C95:C103` (9 rows) contain the string `TIN NOT FOUND`, seeded by
`ImportSuppliersFromJSON.bas:745-813`. All 9 collapse onto a single dictionary key; typing one of
those names writes the literal `"TIN NOT FOUND"` into `PJ!D`.

**B4 — case/whitespace sensitivity inconsistent with the Non-Vat path.**
`dictName` uses binary compare (`modEngine.bas:324`) while `modPJSync.bas:193` uses
`vbTextCompare`. `LoadSuppliers` also starts at row 2 (`:151`), so header cells leak the keys
`TIN#` / `PARTICULARS`.

**B5 — `Sheet9.cls` (PJ Non-Vat2) is a silent no-op.**
It references `START_ROW`, `COL_TIN`, `COL_NAME`, `COL_AMOUNT`, `COL_DEBIT`, `COL_REF`, `COL_COA`,
`COL_FULL_ID` without declaring them and without `Option Explicit`; all resolve to `Empty`, every
column guard fails, and the handler never executes. Its assumed layout also disagrees with the
actual PJ-style header block.

### Not reproduced (missing evidence)
- **0** numeric TIN cells and **0** TIN-like strings found in `PJ!E` / `PJ Non-Vat!E` across all
  populated rows. Leading-zero loss is a latent risk only (no input format/validation at
  `Sheet12.cls:216`), not an observed failure.
- No scanned-document or OCR input exists in this repository. If the report refers to a physical
  document, that input is **not available here** and the defect cannot be reproduced from it.

### Acceptance tests for the fix
- TIN values resolve regardless of dash/space/branch-code formatting.
- Vendor names do not absorb TIN strings; a TIN written into E is flagged, not silently accepted.
- Missing or malformed TINs stay flagged as missing/invalid — never fabricated.
- Existing valid supplier records still parse to the same (deduplicated, approved) master row.
- `PJ!D` cells are text-formatted so leading zeros are preserved.

## 5. Defect C — PJ/CDJ row estimation and dynamic totals

### Reported
Monthly row estimates and totals are sensitive to added non-VAT transactions in CDJ; the bookkeeper
inserts these manually and may adjust row counts.

### Confirmed mechanisms

**C1 — monthly TOTAL rows are frozen `SUM` ranges.**
`CDJ!F674 = SUM(F614:F673)` … `CDJ!U674 = SUM(U614:U673)`; the same pattern at rows 111, 193, 408,
516, 612. The last data row of the final block is 673. Nothing extends these ranges.

**C2 — column T (Sundry Debit) is not summed in ANY total row.**
`T674` is empty, so `W674 = SUM(G674:T674)` and `X674 = V674+W674` are already broken:
cached `X674 = -221,105.45`, `X111 = -343,798.66`. The workbook's own balance checks are non-zero
today.

**C3 — no TOTAL blocks exist for July–December.**
The last month marker is `C674 = "JUNE TOTAL"`. Rows below 674 have no visible monthly total.

**C4 — the next-row pointer is a static number.**
`CDJ!AA14 = 755` (`CDJ_COL_NEXTROW`, `modEngine.bas:50-51`), read blindly by `LoadNextRow`
(`:221-236`). Excel row insertion above row 755 never adjusts it, so after the bookkeeper inserts
rows the engine writes over live/manual rows.

**C5 — last-row and dedupe detection scan the wrong columns.**
`LoadCDJReferences` / `FindCDJRow` scan columns **Y(25) and Z(26)** (`modEngine.bas:200-207`,
`:421-427`). In the real sheet, Y holds only 29 references while **AA(27) holds 574** and AB(28)
holds the single PNV reference. Historical references are invisible to dedupe → duplicate inserts.
`modPJSync.bas:353-366` picks "first row with C empty and Z empty", which today resolves to
**row 215 — a live manual March transaction** (`E215 = "EMPLOYEE CONTRIBUTIONS AND LOANS"`,
`F215 = -17,489.95`).

**C6 — month attribution is carry-forward and can re-bucket.**
`modGLScanEngine.bas:86-88` carries the last exact-name marker in column C. Stray mid-block markers
(`C277="JAN"`, `C322/C371="FEB"`, `C425/C475="APR"`, `C515="MAY"`) sit inside other months' `SUM`
ranges, so the GL month and the visible TOTAL row disagree for the same physical rows.

### Controlled reproduction (temp copy only — source workbook untouched)

Simulated `SyncPJNonVatToCDJ` insert of `PNV-00742` (JUL, Clinic Materials and Supplies, 1,500.00)
at the engine's target row 755:

| Check | Range / value | Covers new row 755? |
|---|---|---|
| `CDJ!F674` (JUNE TOTAL) | `=SUM(F614:F673)` | **No** — 82 rows below range end |
| All other month TOTALs | ranges end ≤ 673 | **No** |
| `modGLScanEngine.ScanCDJ` loop | 15 → `End(xlUp)` of E = **5821** | **Yes** — GL books it |
| Month attribution | `C755="JUL"` → `V8_Month` = 7 | GL/GL_V8_CALC July +1,500; **no CDJ July block exists** |
| `CDJ!W755` | `=SUM(G755:T755)` counts N **and** T | 3,000 vs cash −1,500 → `X = +1,500 ≠ 0` |
| `CDJ!X755` | overwritten by the entry note | balance check destroyed |
| `CDJ!AA14` | 755 → 756 (static) | not adjusted by any row insert |

Net effect: the transaction is **invisible to every visible CDJ monthly total** and **visible to the
GL** in a month that has no CDJ total block.

### Already-proven live exclusion
Sheet `PJ Non-Vat` contains exactly two transactions:

- `PNV-00002` (row 8, 1,500.00) — **0 occurrences anywhere in CDJ** → silently excluded.
- `PNV-00004` (row 9, 1,500.00) — present only as the amountless ghost `AB5677` → excluded from
  every total and from the GL.

### Root causes, ranked
1. **Fixed formula ranges** — monthly totals are frozen `SUM`s; `T` is never summed; no Jul–Dec
   blocks.
2. **Incorrect last-row / next-row detection** — static pointer `CDJ!AA14`; dedupe keyed on
   columns Y/Z while the real references live in AA/AB.
3. **Month-marker flags** — carry-forward `cur` mis-buckets rows below the last marker and around
   stray mid-block markers.

### Acceptance tests for the fix
- Adding a valid non-VAT transaction is included in the relevant CDJ monthly total.
- Existing VAT transactions remain included and are not double-counted.
- Blank/template and `TOTAL` rows are never treated as posted transactions.
- Row insertion or expansion does not corrupt formulas, formatting, macros, or account mappings.
- The row-balance check column X survives every machine write.
- GL and `GL_V8_CALC` agree with the visible CDJ monthly totals for the same rows.
