# v7.9.3 — GL Automation Hardening

Base: `6e4ffd485c6d2c23bdd3a50e8f75200afb8cf2d6` (v7.9.2)

## Review findings carried forward

1. `PLAN v1.md` requires the sequence **Posted Journals → Account aggregation → Monthly GL balances → COA presentation → Chart** and explicitly separates accounting calculation from `Graphify`. 
2. The v7.9.2 workbook evidence contains a `GL_AUDIT` reconciliation sheet and records an unmapped `GJ` account, `Cost of Revenue`, for `1,139`; therefore a balanced known-source population must not be represented as a fully mapped GL result.
3. The workbook contains journal sheets `PJ`, `PJ Non-Vat`, `CDJ`, `SJ`, `CRJ`, and `GJ`, plus `GL` and `SUPPLIERS DATA`.
4. The implementation must not infer accounting mappings from chart/numeric-column detection.

## v7.9.3 implementation scope

### A. Deterministic mapping
- Discover required journal columns by explicit header labels where possible.
- Keep source-sheet mappings explicit and centralized.
- Never use `Graphify` to select accounting columns.
- Treat missing/ambiguous mappings as `UNKNOWN`, not as zero.

### B. Journal aggregation
- Aggregate only rows that are explicitly considered posted by the configured posting rule.
- Normalize account names before dictionary lookup.
- Aggregate Debit and Credit independently by `Account + Year + Month`.
- Preserve an unmapped ledger for any journal line that cannot resolve to the approved COA.

### C. GL calculation
- `Net Movement = Debit - Credit`.
- `Ending Balance(M) = Ending Balance(M-1) + Net Movement(M)`.
- January uses the configured opening balance.
- Do not silently zero a failed extraction, failed mapping, or missing opening balance.

### D. Validation
- `ValidateGLConsistency` must validate the actual extracted population, not return a constant `True`.
- Controls must report:
  - total debits
  - total credits
  - difference
  - mapped amount
  - unmapped amount
  - mapping status
- A balanced journal population is not sufficient to certify a complete GL if unmapped accounts remain.

### E. COA coverage
- Validate every configured GL account across 12 months.
- Expected matrix: `46 accounts × 12 months = 552 account-month results`.
- Report accounts with activity but no COA mapping.

## Acceptance gates

**G1 — Mapping:** all required journal fields resolve explicitly or are reported `UNKNOWN`.

**G2 — Extraction:** each supported source returns a deterministic row population; no placeholder zero result.

**G3 — Reconciliation:** source Debit = source Credit within tolerance for the included population.

**G4 — COA coverage:** all mapped journal activity is represented in the GL matrix; unmapped activity is separately reported.

**G5 — Running balance:** January opening balance and subsequent monthly carry-forward are proven for every active account.

**G6 — Workbook integration:** only after G1–G5 pass should the workbook `GL` sheet be overwritten by automation.

**G7 — Graphify:** charting is downstream of proven GL values.

## Known blocker for the binary workbook

The GitHub connector can write UTF-8 source files but cannot safely upload an `.xlsm` binary through its text-file API. Therefore v7.9.3 keeps the VBA implementation source-controlled as `.bas`; the binary workbook must be installed/tested through Excel or a normal Git client before treating the workbook artifact as updated.
