### The biggest technical issue I see

The rebuilt workbook appears to have been constructed by **adding the mapping/audit/calculation sheets while preserving the existing VBA byte-for-byte**.

The manifest explicitly says:

> `values_or_formulas_changed: false`
> `macros_changed: false`

And the verification script checks that `vbaProject.bin` is byte-identical between v8.0 and v8.1.

That is good for preservation, but it creates an important question:

**Does the VBA actually know about the newly added `COA_MAP` / `GL_V8_CALC` design?**

The repository contains two different GL-engine generations.

`modGLAggregation.bas` contains the older deterministic engine and its `RefreshGL` ultimately builds `GL_V8_CALC` while keeping the existing GL protected. But `modGLRefresh.bas` contains a different implementation that explicitly writes the existing GL and has a comment indicating:

`46x12 GL filled from CDJ+CRJ`

There is therefore a **real implementation-consistency issue to resolve before calling v8.1 production-ready**.

The repository's `status_v2.md` also correctly documents that the earlier v8.0 state was only:

**POC — Reconciliation PASS / COA Mapping HOLD**

and that runtime VBA behavior had not yet been certified.
